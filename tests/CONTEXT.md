# tests

Parent: [../CONTEXT.md](../CONTEXT.md)

## Purpose

Checks over `docs/examples/` and the pinned `living-doc-collector-gh` and `living-doc-toolkit`: the static corpus check, the snapshot stage over `docs/examples/`, and the testbed stage over `AbsaOSS/living-doc-testbed`'s `core`. Also two pages checked against the installed `living-doc-utilities` (the authoring guide's before/after pairs, the error codes), the retired-names check over this repository and the three pinned components, the page rules over this repository's pages (`docs/`), and the drift check of `docs/_backlog/debt-overview.md` against GitHub. The local integration runner (`integration/`), run by hand for a milestone. Stages, layout, the workflow diagram and the failure table: [README.md](README.md).

Not here: the agentic layer's tests, which sit next to each script in `agentic/` ([agentic/CONTEXT.md](../agentic/CONTEXT.md)).

## How it fits

- `examples-check.yml` runs `examples/examples_check.py` (the corpus, then the guide's pairs and `docs/reference/errors.md`), then pytest over `examples/`, `docs/` and `integration/`; `docs/test_page_structure.py` checks every page against CONTRIBUTING.md § Writing documentation, with the page, card and redirect lists and the hand-written parser in `docs/pages.py` (ported from `living-doc-generator-markdown`; no Markdown library).
- `retired-names.yml` clones each component at its pin and runs `docs/retired_names_check.py --strict` over them and this checkout, on every PR and push to `master`.
- `debt-overview.yml` runs `docs/debt_overview_check.py`, the only check here that reads the GitHub API (open issues of the seven repositories, by the four labels; `GITHUB_TOKEN` or `GH_TOKEN` when set). It imports `section` from `docs/pages.py`; `docs/test_debt_overview_check.py` parses the real page offline, so `examples-check.yml` catches a `pages.py` change that breaks it. Its tests replace GitHub with a set, a map or a stub `_get` and never go online. Exit 1 is drift only; anything GitHub answers that it cannot read is exit 2.
- `real-collector.yml` runs `examples/regen-collector-snapshots.sh` (snapshot job) and `testbed/run-testbed-stage.sh` (testbed job). Both source `collector/collector-gh.sh` and `collector/toolkit.sh`, the single definitions of the pinned components, their venvs and their runs. `toolkit.sh` uses `native_dir` and `_collector_gh_venv_python` from `collector-gh.sh`, so it is sourced after it.
- `integration/local-integration.sh [--check]` runs the source-code chain for one project: it clones `collector-gh`, `toolkit`, `generator-markdown` and, for `TARGET=testbed`, the testbed into `out/` (git-ignored, reused across runs), writes only those clones' `.env.local`, and runs each component's own `local-integration.sh`: the collector once, then the toolkit and the generator per view into `<OUT_DIR>/<view>/`, then `examples/check_utilities_pins.py --strict --requirements …` over the clones into `<OUT_DIR>/pin-report.txt`. A `TARGET=testbed` run then judges its output, the release go/no-go: `testbed/check_testbed_stage.py core` over `<OUT_DIR>/collector-gh/`, `testbed/check_testbed_toolkit_stage.py --runner` over both views, each in the venv its component's script built in its clone (`.venv-local-integration/`), then the six documents and their run reports; the first failure exits non-zero and its last line names the check. A `TARGET=project` run is not judged. Its configuration is `integration/.env.local` (git-ignored; keys and rules in `.env.local.example`), read as data; relative paths resolve against the repository root. No workflow runs it; `integration/test_local_integration.py` covers, offline, its refusals before any clone and the chain over stand-in components. A run first clears the paths the chain writes in the root, nothing else there; a failure also ends the root's `local-integration.log`. It refuses an `OUT_DIR` at or inside the target's checkout, `out/testbed/` or `out/components/`. Its `target:` line counts untracked files as changes, since the collector mines them; the `living-doc` and component lines count tracked changes only, as the component scripts do. A reused clone whose `origin` is another repository, or a link (at the clone or its `.git`) to an existing checkout, is cloned again, and a link further down `out/`, such as `out/components/`, stops the run; and after its checkout every clone is cleaned: `git clean -ffd` in a component, which keeps its ignored `.env.local` and venv, `-ffdx` in the testbed. How a milestone uses it: `docs/_integration/README.md`. Its `--check` runs only the collector's own `--check`: the toolkit's and the generator's stop on a missing input file, which only a run writes, so in a run each component's `--check` runs right before it.
- Pins: the component refs only in `collector/collector-pins.env` (`COLLECTOR_GH_REF`, `TOOLKIT_REF`, `GENERATOR_MARKDOWN_REF`); the checker's `living-doc-utilities` in `examples/requirements-examples-check.txt`. `examples/check_utilities_pins.py` warns on a minor-version skew between the four (`--strict` fails); `real-collector.yml`'s snapshot job and the local integration runner run it with `--strict`. `GENERATOR_MARKDOWN_REF` is run only by the local integration runner, never by a workflow; CI reads it in the pin report and the retired-names workflow.

## Conventions

- Python files are standalone scripts. Add type hints to new public functions.
- Checkers report problems as data (`examples_check.Finding`: file + rule), never through `logging`.
- Shell runners need bash 3.2+ (macOS) and run from any directory.
- CI uses Python 3.14; the collector stages need 3.10 or later.
- `examples/check_collector_stage.py` and `testbed/check_testbed_stage.py` run in the collector's venv, `examples/check_toolkit_stage.py` and `testbed/check_testbed_toolkit_stage.py` in the toolkit's, none in the checker's. In the local integration runner, the venv is the one the component's own `local-integration.sh` built in the runner's clone.
- `testbed/check_testbed_toolkit_stage.py` reads two layouts, the stage's (`gh-headers/`, `tests/`) and the runner's (`--runner`: `<view>/toolkit/<command>/`, a matrix and a catalog per view); `testbed/check_testbed_stage.py core` reads both callers' collector output as it is. A change to a check reaches both callers.
- The toolkit's venv is reused only for the same interpreter and the same `TOOLKIT_REF`, not the same `requirements.txt`: its packages are installed by path, so a new ref with the same file would keep the old code.

## Invariants and gotchas

- Deterministic: no LLM call in any checker or the normalizer. The only network access is fetching pinned inputs (each component's clone, `git ls-remote` and `requirements.txt`, `pip` from PyPI, `normalisation_cases.yaml` at the installed `living-doc-utilities` tag) and checking out the testbed. No pytest test goes online: fetchers are injected.
- The retired-names check reads tracked files only (`git ls-files`) and skips every `tests/` directory: tests quote retired names to prove they are rejected. A hit that is not a use goes into `docs/retired-names-allow.txt` with its reason; an entry that skips no hit fails the check.
- A pin bump is a reviewed change: regenerate `docs/examples/_expected/` in the same PR and keep the testbed stage green; a bump of `GENERATOR_MARKDOWN_REF` alone regenerates nothing. A move of the checker's `living-doc-utilities` version fails `examples/examples_check.py` until the before/after pairs in `docs/guides/authoring-documentation.md` and the codes in `docs/reference/errors.md` match it (root `CONTEXT.md` § Conventions).
- The testbed stage reads the testbed at `master`, never pinned to a SHA; the local integration runner reads `master` too unless its `TESTBED_REF` names a tag or full SHA. Nothing about `core`'s content (counts, ids) is written here; every value comes from the checkout at run time. Any warning over `core` is a defect.
- The toolkit stage reads the collector's raw output, never `docs/examples/_expected/**`, and nothing is written under the output directory until every check passed.
- The stage only reads the testbed and fails if its `git status` changes. Never write into the testbed.
- A problem the collector must report is a derived case: a function in `testbed/testbed_cases.py` that changes a copy of `core`, finds its target by structure (never by literal text) and returns the one warning code the run must report. Never a patch file or a testbed change ([testbed/negative-cases.md](testbed/negative-cases.md)).
- A check or case that stops fitting a valid `core` is fixed here, never in the testbed.
- Mining behavior is tested by the collector stages, never by a pytest unit test.
- The runner's testbed settings copy `testbed/run-testbed-stage.sh`'s (`PROJECT_ID`, `core`'s three `doc-source` folders, the whole test tree for `ui-tests`): change both together.
- The runner's trust model: the operator writes its configuration and owns `out/` and the output root. The runner guards against an operator's plausible mistakes: an unknown key, a ref that is not a tag or full SHA, an output root inside a checkout or clone, a clone of another repository or a link to an existing checkout in `out/`, an untracked file in the target. It does not guard against links crafted inside the output root or inside its own clones, a target checkout inside its clones, or git-ignored files in the target's configured folders. A review finding of that kind is answered with this rule, not with code.
- The runner refuses an unknown key, where the component scripts ignore one: a misspelt ref key would otherwise run the pin unnoticed. Its tests write a pins file of their own, full SHAs (`TEST_PINS`), never the real one: a real pin that is a tag would need the fake `git` to know it. They replace `git` on `PATH`: for the refusals a `git` that fails anything but `ls-remote`, so a clone would show; for the chain a `git` whose `clone` drops a stand-in `local-integration.sh`. The chain test also checks the collector's testbed settings against `testbed/run-testbed-stage.sh`'s. The stand-ins write `docs/_integration/MS1/testbed-core/`, a real run's warning-free outputs, so the verdict's toolkit check runs for real and needs `living-doc-utilities` in the pytest interpreter; the collector check is a stand-in, since the real one reads the testbed's own files. If the checker's `living-doc-utilities` moves to a contract those outputs no longer validate against, point `MS1_OUTPUT` at a newer committed testbed run.
- generator-markdown clears `<view>/generator-markdown/` as a whole, so the runner writes the generator's log beside it, at `<view>/local-integration.log`. Every log the runner writes is named `local-integration.log`, which `docs/_integration/.gitignore` ignores.
